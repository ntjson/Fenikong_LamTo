# Predict the price band with a model, and fall back in the open

A Price comparison used to read a fixed row out of
`src/lamto/finance/fixtures/reference_prices.json`, which made "the system knows
what this job should cost" a lookup table wearing a claim it could not support.
The band is now generated by the same OpenAI-compatible provider the triage
assistant already uses, grounded on that fixture, and the fixture is kept as the
fallback rather than the answer. Elevator is the only category with grounding, so
it is the only category that gets a band.

## Considered options

Keeping the fixture and having the model write only the explanatory sentence was
rejected: it dresses a constant as a prediction, which is the failure mode the
change exists to remove. Training a model offline on synthetic data was rejected
as unbuildable in the time available and unanchorable to a line of real code.

## Consequences

**The quotation amount is withheld from the prompt.** Given the figure a manager
typed, a model will reason toward it, and the percentage that comes out the other
end measures nothing. The model receives the category, the scope text and the
Reference price set; the comparison arithmetic happens in Python afterwards.

**Fallback is visible, never silent.** Provider error, timeout past eight
seconds, contract violation, or refusal all fall back to the Reference price
band, and the interface says so. A product whose argument is accountability
cannot quietly substitute one number for another.

**The comparison is requested over `fetch`, not by submitting the form.** The
create-proposal form carries an uploaded quotation PDF that a full round-trip
would discard — the reason the original comparison was computed client-side at
all. The endpoint takes JSON and leaves the form untouched.

Tests run with the provider unset and therefore exercise the fallback path; the
predicted path is covered by stubbing the provider.
